## เริ่มและค้นหา PDCA

แบบที่เจ้าของยืนยันใช้ปุ่ม **สร้าง PDCA** ในหน้า Workspaces กรอกชื่อแล้วเปิด Canvas เปล่าเพื่อเพิ่ม Node ภายหลังได้ เมื่อกรอกแต่ช่องว่างให้แสดง “กรุณากรอกชื่อ PDCA” ชื่อซ้ำกันได้ แต่รายการแต่ละใบมีรหัสของตัวเองและเปิดผังตามรหัสนั้น การเปลี่ยนชื่อจึงเปิดงานเดิมได้ตามปกติ

ช่องค้นหาใน Workspaces ค้นจากชื่อ PDCA และข้อความที่บันทึกแล้วใน Node ที่เปิดดูได้ เมื่อเจอข้อความใน Node ให้แสดงทั้งชื่อ PDCA และชื่อ Node เพื่อเลือกเปิดไปยังจุดที่พบ หากไม่เจอให้แสดง “ไม่พบรายการที่ตรงกับคำค้น” พร้อมให้ล้างคำค้นได้

เกณฑ์ตรวจคือสร้าง PDCA เปล่าสองรายการชื่อเดียวกันแล้วเปิดได้ถูกผัง เปลี่ยนชื่อหนึ่งรายการแล้วค้นด้วยชื่อใหม่ ชื่อ Node หรือเนื้อหา Node ที่บันทึกแล้ว และเปิดไปยัง Node ที่เลือกได้จากผลค้นหาในแอปตาม Closure-01 [D-040, D-075, D-080 และ D-082](https://github.com/FillGH/THE_NODE_OF_PDCA/blob/edd8d9832b2f54d4cb8ea66d46e603e98d701e96/PROJECT.md#L849)

## บันทึก แก้ไขร่วมกัน และกู้ draft

[ตารางตรวจรับ Collaboration](qa/COLLABORATION_ACCEPTANCE.md) กำหนดกรณี C-01–C-11 จากชุดสมมติเดียวกัน รวมผลบันทึกตอบกลับช้า การชนฉบับ สลับแท็บ ปิดทุกหน้าต่าง/คืนแท็บ และจบ Session ก่อนส่งต่อเครื่อง ผลตอบกลับถึงผู้แก้กับการที่ Host บันทึกข้อมูลเป็นคนละเหตุการณ์ ผู้ชมได้ฉบับที่ Host บันทึกแล้ว ส่วนผู้แก้ต้องจับคู่ผลกับชุดข้อมูลที่ส่งและคง draft ที่พิมพ์ต่อ หากหลุด LAN ให้ตรวจสิทธิ์ สถานะ Node แท็บ lock และฉบับล่าสุดก่อนกู้ พร้อมให้ผู้ใช้ยืนยันก่อนส่ง draft ใหม่

Phil ยืนยันให้ Pilot ใช้เครื่องแยกกันและกู้ draft จากเครื่องเดิมเฉพาะใน Session เดิมที่ยังอยู่ การเปิดใหม่หลังปิดเบราว์เซอร์ทั้งหมดเห็นเฉพาะฉบับที่บันทึกแล้ว แม้คืนแท็บอัตโนมัติ เกณฑ์เดิมให้ใช้ **จบ Session** ก่อนส่งต่อเครื่อง หากจะใช้เครื่องร่วมใน Pilot ต้องตกลงวิธีแยกผู้ใช้กับ IT ก่อน เพราะ Display Name และ Session ID เป็นข้อมูลสำหรับแสดงและประสานงาน

[ต้นแบบ Collaboration & Recovery](prototypes/DESIGN_collaboration-recovery.html) จำลอง A/B ในหน่วยความจำของหน้าเดียว รายงานเดิมระบุว่าผ่าน 9 ชุดตรวจระดับเดโมและ Phil รายงานว่าสถานการณ์ “เครื่องเดิม ผู้ใช้คนถัดไป” ผ่าน รอบนี้เพิ่มปุ่มให้ Host จำลองประมวลผลและส่งผลคนละจังหวะ ตรวจผลมาช้า ผลซ้ำ การเชื่อมกลับ คำขอหลังเสียล็อก และการจบ Session ระหว่างรอผลได้บนหน้าเดโม ผลบนระบบรวมและการปิดเบราว์เซอร์จริงยังอยู่ใน C-03/C-04/C-08/C-09

## History และ Trash

| ตัวอย่างหน้าจอ | พฤติกรรมที่เสนอ |
| --- | --- |
| **History → ข้อความ** · `r3 ปัจจุบัน` · `r2` · `r1` | แสดงข้อความ ชื่อที่ผู้แก้กรอก และเวลา เปิดดูข้อความก่อนยืนยัน “กู้ข้อความฉบับนี้” เช่น กู้ `r1` สร้าง `r4` โดยยังเห็น `r1–r3` |
| **History → ประเภท Node** · `Fact → Action` | กู้เฉพาะประเภทเป็นเหตุการณ์ใหม่ คงข้อความ รูป เอกสาร เส้น และ ID เดิม ถ้าเปลี่ยนออกจาก Action ให้ซ่อน PIC, Due Date และ Status แล้วแสดงค่าเดิมเมื่อกลับเป็น Action |
| **ลบ Node** · “รอยรั่วกระจุกอยู่ช่วงเริ่มกะ · 2 เส้นเชื่อม · กู้ได้ 7 วัน” | ยืนยันก่อนย้ายเข้า Trash การ์ดที่เชื่อมอยู่ยังใช้งานได้ เส้นที่เกี่ยวข้องถูกซ่อน |
| **Trash → Node** · “รอยรั่วกระจุกอยู่ช่วงเริ่มกะ · หมดอายุ 15 พ.ย. 09:30 · กู้คืน” | กู้จากรายการได้โดยตรง ถ้าบางเส้นยังกลับมาไม่ได้ ให้บอกสั้น ๆ ในรายการก่อนกด เช่น “กู้ได้ 1 จาก 2 เส้น อีก Node ยังอยู่ใน Trash” เมื่อกู้เสร็จแสดงผลจริง เส้นเดิมกลับมาเมื่อปลายทั้งสองใช้งานได้และเส้นนั้นยังถูกเก็บอยู่ |
| **Trash → PDCA** · “ซองรั่วหลังซีล · ดูวันหมดอายุ · กู้ PDCA” | การลบหรือกู้ทั้ง PDCA จัดการเป็นชุดพร้อม Nodes และเส้นที่เกี่ยวข้อง ระบบลบถาวรอัตโนมัติเมื่อครบ 7 วัน ผู้ใช้ที่ได้รับอนุญาตทำ Delete/Restore ได้โดยไม่มีขั้นอนุมัติ การไม่เปิดใช้งาน PDCA ไม่นำไปสู่การลบ |
| **Audit → ตัวอย่าง** · `Delete to Trash / N-02 / 08 พ.ย. 09:30 / ผู้ทดสอบ / S1` | บันทึก Delete, Restore และ Automatic Permanent Purge ทั้ง Node และ PDCA พร้อม ID และเวลา เหตุการณ์จากผู้ใช้แสดง Display Name และ Session ID เมื่อมี ส่วน purge แสดง “System Operation” |

เก็บ History ของข้อความ ประเภท Node การสร้าง/ลบเส้น และ Status/Due Date ของ Action ตลอดเวลาที่เก็บ Node/PDCA รวมช่วงอยู่ใน Trash เมื่อ purge ให้ลบ History ในแอปของรายการนั้นด้วย อายุการเก็บเหตุการณ์ Audit หลัง purge และผลต่อสำเนาใน Backup ต้องตกลงกับ IT โดยเฉพาะ การเพิ่มหรือเอาภาพออกตามปกติไม่มี History หรือปุ่มกู้รายภาพแยกต่างหาก


### เกณฑ์ History/Trash และช่วงเริ่มเก็บ

บันทึกพร้อมการเปลี่ยนที่เก็บสำเร็จ ใช้ ID และเวลาในข้อมูลที่บันทึก ชื่อผู้แก้เป็นชื่อที่กรอกเอง คำขอที่ล้มเหลว ซ้ำโดยไม่มีการเปลี่ยน หรือ draft ที่ยังไม่ได้ส่ง ไม่เพิ่มประวัติการเปลี่ยน กำหนดให้การเก็บเริ่มตั้งแต่ช่วงที่การกระทำนั้นเปิดให้ใช้ ส่วนหน้าจอ History, Restore และ Trash อยู่ช่วงที่ 3

**แบบที่ Phil รับรอง** เก็บ Audit การลบ/กู้/purge ของ Node หรือ PDCA ที่ลบถาวรไว้ 1 ปีนับจากวัน purge จริงตามวันโรงงาน ให้เฉพาะ IT เปิดดู การใช้วัน purge ทำให้รายการที่ไม่มีการใช้งานเกินปียังมี Audit หลังลบครบ 1 ปี เก็บรหัสรายการ เหตุการณ์ วันเวลา และข้อมูลผู้ดำเนินการตาม Closure-04 พร้อมวันหมดอายุ Trash เมื่อเกี่ยวข้อง แยกจากเนื้อหาและ History ของงาน ทดสอบ H-06 ด้วย Workspace ที่ไม่ได้ใช้งานมานานกว่าหนึ่งปีแล้วจึงสั่งลบ ตรวจว่า Audit ยังอ่านได้หลัง purge และหมดอายุตามรอบที่เลือก

## แผน Host, สิทธิ์ และ Backup สำหรับส่งต่อให้ IT

เจ้าของโครงการเลือกใช้ **laptop เป็น Host ชั่วคราว** แล้วให้ IT เตรียมเครื่องหลักในขั้นถัดไป โดยใช้กลุ่มผู้ได้รับสิทธิ์เข้า **Project Float Monitor** เป็นกลุ่มผู้ใช้ PDCA ภายใน LAN โรงงาน ให้ IT จัดการสิทธิ์และดูแลให้โปรแกรมรันบน Host พร้อมเก็บ Backup บน Host แบบหมุนเวียน **30 วัน** เจ้าของแจ้งว่าเคยทำรูปแบบนี้กับ Float Monitor แล้ว จึงใช้เป็นข้อมูลประกอบการเตรียม Host และสิทธิ์ของ PDCA การตรวจบนเครื่องจริงของ PDCA เป็นหลักฐานคนละชุด

| เรื่อง | สิ่งที่ยังต้องยืนยันหรือทดสอบ | ผู้รับผิดชอบที่เสนอ |
| --- | --- | --- |
| LAN และการอนุญาต (G-11) | Phil มอบให้ทีม IT กำหนดและจัดการสิทธิ์เข้าถึง IP ของ Host สำหรับกลุ่ม Float Monitor บน Desktop ที่ได้รับอนุญาตบน LAN โรงงาน เก็บผลทดสอบการอนุญาต ปฏิเสธ และถอนสิทธิ์ตาม G-11 | IT + เจ้าของโครงการ |
| Host และต้นทุน | Phil ยืนยันว่า laptop พร้อมเป็น Host ชั่วคราวบน LAN และทำแบบที่เคยใช้กับ Float Monitor ได้ ให้ IT เลือกวิธีให้แอปและงานสำรองเริ่มเองหลังเปิดเครื่องโดยไม่รอ Phil ล็อกอิน พร้อมตรวจพื้นที่สำหรับ Backup 30 วัน เก็บหลักฐานของ PDCA ในช่วง 4 / VERIFY ก่อนย้ายให้ตรวจทรัพยากรและความเข้ากันได้กับ Float Monitor ใช้ทรัพยากรเดิมโดยไม่มีค่าใช้จ่ายใหม่ | IT + เจ้าของโครงการ |
| Draft และ Audit | ใช้เครื่องแยกกันตามที่ Phil ยืนยัน และทดสอบการแยก draft ระหว่าง Session หากจะใช้เครื่องร่วมให้ทบทวนวิธีแยกผู้ใช้กับ IT ก่อน Phil รับรองแบบ Audit และ Restore ตาม IT-05/IT-06 การใช้กับข้อมูลโรงงานต้องผ่านขั้นอนุญาตของ IT/ผู้กำกับข้อมูล | IT/ผู้กำกับข้อมูล + เจ้าของโครงการ |
| การดูแลต่อเนื่อง | Phil มอบให้ทีม IT รับผิดชอบการดูแลหลัก การรับช่วง และด้านเทคนิค ให้ IT จัดผู้ดูแลหลัก/สำรองและช่องทางรับแจ้งเมื่อ Backup ล้มเหลวหรือดิสก์ใกล้เต็มก่อน Official Pilot ตาม D-067 / Closure-05 | IT |

ก่อนตัดสินใจ BUILD ให้ทบทวนความพร้อมของ Host วิธีจำกัดสิทธิ์ และแผน Backup/Restore กับ IT ส่วนผลทดสอบการเข้าใช้บน LAN และผลซ้อมกู้ข้อมูลจริงเป็นหลักฐานที่ต้องเก็บก่อน Pilot ตามเกณฑ์ของโครงการ

**ประเมินพื้นที่และการเดินงาน** รอบทุก 2 ชั่วโมงเท่ากับได้ถึง 360 จุดใน 30 วันถ้า Host เปิดตลอด ให้ IT ประเมินพื้นที่จากข้อมูลรวมรูป ขนาดชุดสำรอง และพื้นที่พักตอนสร้าง/ซ้อมกู้ ทดสอบกรณีสำรองครั้งแรกหลังเปิดเครื่อง รอบสำรองล้มเหลว และพื้นที่ใกล้เต็ม ตรวจความสำเร็จจากชุดที่สร้างเสร็จและยืนยันว่าอ่านคืนได้ เก็บเวลา จุดข้อมูล และผลตรวจเพื่อใช้เทียบ RPO/RTO

**Backup/Restore ที่จะนำไปซ้อม** เจ้าของกำหนดให้สำรองอัตโนมัติทุก **2 ชั่วโมงขณะ Host เปิด** ถ้าล้มเหลวให้แจ้งผู้ดูแลหลักและลองใหม่โดยเร็ว วัดอายุจาก snapshot ล่าสุดที่ตรวจว่าใช้กู้ได้ สำรองข้อมูลที่บันทึกแล้วทั้งชุดบน Host แบบสอดคล้องกัน รวม PDCA, Nodes, เส้น, รูป, ลิงก์, History และข้อมูล Trash ที่ยังเก็บอยู่ เก็บ snapshots แบบหมุนเวียน 30 วันแยกจาก Trash 7 วัน เป้าหมายคือ RPO ≤ 4 ชั่วโมงเมื่อยังมี Backup ใช้ได้ และ RTO ≤ 1 วันทำการเมื่อมีโครงสร้างพื้นฐานและผู้ดูแลพร้อม ความเสียหายที่ทำลายทั้งข้อมูลและ Backup บน Host เดียวกันกู้จากชุดนี้ไม่ได้

1. เฉพาะทีม IT และ Phil มีสิทธิ์กู้ระบบจาก Backup ผู้กู้เลือก snapshot ที่ยืนยันความสมบูรณ์ได้ บันทึกเวลาของข้อมูลในชุดนั้นและเวลาที่เริ่มกู้ กติกานี้ใช้กับ Backup ของระบบ ส่วนสิทธิ์ Restore ใน Trash ของแอปใช้ตาม D-037/D-044
2. ซ้อม Restore ในพื้นที่แยกก่อน ตรวจจำนวนและ ID ของ PDCA/Nodes/เส้น เปิดรูป ตรวจลิงก์อ้างอิง และเทียบ History กับ Trash รวมถึงทดสอบการเข้าใช้จากเครื่องที่อนุญาตและเครื่องที่ต้องถูกปฏิเสธ
3. Phil ยืนยันให้ IT ตรวจรายการลบที่เกิดหลังเวลาของ snapshot ในพื้นที่แยก คงสถานะ Trash และวันหมดอายุเดิมสำหรับรายการที่ยังมีสิทธิ์กู้ และคัดรายการที่ถูก purge ออกก่อนเปิดให้ใช้ หากหลักฐานไม่ครบให้เก็บชุดกู้ไว้ในพื้นที่แยกจนกว่า IT จะตรวจยืนยันได้ บันทึกผลเทียบ RPO/RTO และขั้นตอนย้อนกลับถ้ากู้ไม่ครบ
4. เมื่อย้ายจาก laptop ไป server ให้หยุดรับการแก้ไขที่ต้นทางชั่วคราว ทำ snapshot รอบสุดท้าย แล้วตรวจเทียบต้นทางกับปลายทางด้วยรายการเดียวกัน ทดสอบ Float Monitor และสิทธิ์ LAN ก่อนสลับ ให้มี Host ที่รับการเขียนเพียงเครื่องเดียว และมีแผนย้อนกลับที่จัดการงานใหม่หากสลับแล้วเกิดปัญหา

**หลักฐานเมื่อกู้ Backup เก่า · แบบที่ Phil รับรอง** ใช้ Audit การลบ/กู้/purge บน Host ที่แยกจากข้อมูล Workspace ที่ถูกย้อน ให้แต่ละ snapshot อ้างจุดตัดของลำดับเหตุการณ์ที่สอดคล้องกับข้อมูลในชุดนั้น IT ตรวจตาม ID และลำดับจากจุดตัดถึงก่อนเริ่มกู้ รวมการกู้จาก Trash ที่เกิดหลัง snapshot เพื่อรักษาสถานะล่าสุดเท่าที่หลักฐานยืนยันได้ เกณฑ์ตรวจรับคือรายการที่เข้า Trash ยังซ่อนและใช้วันหมดอายุเดิม รายการที่ purge แล้วถูกคัดออก และการกู้ซ้ำไม่คืนรายการที่ถูก purge หาก Audit หาย ขาดช่วง หรือยืนยันจุดตัดไม่ได้ ให้คงชุดที่กู้ในพื้นที่แยกจน IT ยืนยันได้ ทดสอบทั้งกรณีที่หลักฐานครบและมีช่องว่าง
